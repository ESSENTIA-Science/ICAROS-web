# 14 — 레거시 Posts · 이미지 이관 계획

> 레거시 Supabase 에 남아 있는 게시글 19건과 그 안의 이미지 48장을 ESSENTIA Community 로 옮기고,
> 본문의 Supabase 절대 URL 을 새 위치로 고쳐 쓰는 작업.
>
> **이 문서는 실행 전 계획이다.** 실제 쓰기는 D1(ESSENTIA 서비스 토큰)과 상대 팀 협조가 필요하고,
> 그 두 가지가 이 저장소 밖에 있다. 여기서는 **우리가 지금 끝낼 수 있는 것**과
> **상대에게 넘겨야 하는 것**을 나눈다.

---

## 0. 지금 확인된 사실 (실측)

| | 값 | 확인 방법 |
|---|---|---|
| 이관 대상 글 | **19건** (`included`) | `docs/legacy-dump/posts-payload.json` |
| 제외 | 1건 — 제목·날짜가 ESSENTIA 기존 글과 일치 | 같은 파일 `skipped` |
| 대조 필요 | 1건 — `ICX-1A Launch`, 같은 사건 글이 이미 있을 수 있음 | 같은 파일 `review` |
| 본문 내 이미지 참조 | **48건, 전부 `<supabase-host>` 절대 URL** | 본문 정규식 스캔 |
| 고유 이미지 | **48개** (URL·내용 모두 중복 0) | md5 대조 |
| 원본 총량 | **85.2 MB** (png 8 · jpg 21 · jpeg 19) | 전량 내려받아 실측 |
| 정책 상한 초과 | **21개가 2MB 초과** | `UPLOAD_POLICIES` 대조 |
| Supabase 생존 | **살아 있음** (HTTP 200, 4MB 이미지 응답) | 오늘 실측 |
| 작성자 | 레거시에 작성자 데이터 **전무** → ICAROS 서비스 계정 FK 로 전건 귀속 | D13 |

**이미 해 둔 것**: 48장 전량을 로컬로 내려받아 무결성(md5)까지 확인했다. Supabase 가 내일 죽어도
바이트는 잃지 않는다. 다만 **그 사본은 추적 밖**이므로 백업 위치를 정해 두어야 한다(§5).

## 1. 이 작업이 쉽지 않은 진짜 이유

두 개의 벽이 있고 **둘 다 우리 쪽에서 열 수 없다.**

### 벽 ① 글을 넣을 수 없다

`/posts` 의 단일 원본은 ESSENTIA Community 다 (D1·D23). 우리는 **읽기만** 한다.
쓰기는 D1 서비스 토큰이 필요하고 아직 없다. DB 직접 쓰기는 `public` 이 ESSENTIA 단독 소유라
(D2) 애초에 권한이 없다 — 오늘 실측으로 `public.flyway_schema_history` 조차 못 읽는 것을 확인했다.

D13 이 "레거시 import 는 D1 이전에 **DB direct** 로 넣는다"고 적어 둔 것은
**ESSENTIA 쪽에서 넣는다**는 뜻으로 읽어야 한다. 우리가 하는 일이 아니다.

### 벽 ② 이미지를 넣을 자리가 우리 것이 아니다

ESSENTIA 는 게시글 이미지를 `/api/forum/image/{name}` 으로 서빙하고, 그 실체는 공유 버킷의
`forum/` 프리픽스다. 우리 코드는 그 프리픽스를 **읽을 수는 있어도 쓸 수 없다** —
`isOwnedKey` 가 `forum/` 을 일부러 제외하고 있고(07 §2), 오늘 새로 만든 IAM 정책도
`icaros-web/*` 로만 잘려 있다. 프리픽스 포함관계로 인한 교차 삭제 사고 전력 때문에
**의도적으로 세운 경계**이고, 이관 편의를 위해 허무는 것은 나쁜 거래다.

## 2. 갈림길 — 이미지를 어디에 둘 것인가

**이 결정이 나머지 전부를 정한다.** 세 안이고, 하나는 우리끼리 끝낼 수 있다.

| | 안 | 이미지 위치 | 본문 URL | 우리가 할 수 있나 | 대가 |
|---|---|---|---|---|---|
| **A** | ESSENTIA 업로드 API 경유 | `forum/` | `/api/forum/image/{name}` | ❌ D1 토큰 필요 | 가장 깨끗. Community 가 자기 이미지를 자기 규칙(MIME 검증·감사 로그)으로 갖는다 |
| **B** | 우리 버킷에 두고 우리가 서빙 | `icaros-web/media/` | `https://icaros.kr/api/media/{id}` | ✅ **지금 가능** | 상대 게시판이 우리 가동률에 묶인다. 우리가 죽으면 그쪽 글의 이미지가 깨진다 |
| **C** | 상대에게 파일만 넘기고 그쪽이 올림 | `forum/` | `/api/forum/image/{name}` | ⚠️ 파일 전달까지만 | 이름 매핑을 상대가 만들고 우리는 그 결과로 본문을 고쳐야 한다 — 왕복 한 번 더 |

**권고: A 를 목표로 하되, D1 이 늦어지면 B 로 간다.**

근거는 소유권이다. 게시글은 Community 의 것이므로 그 이미지도 Community 가 갖는 편이 맞고,
D1 이 어차피 필요한 작업이라 A 는 "따로 드는 비용"이 아니다.
B 는 되돌리기가 쉽다는 점이 장점이다 — 나중에 A 로 옮길 때 본문 URL 만 한 번 더 치환하면 된다.
**C 는 피한다.** 이름 매핑이 사람 손을 거치면 48건 중 하나는 반드시 어긋난다.

## 3. 지금 끝낼 수 있는 것 (D1 없이 · 우리 쪽만)

### 3.1 원본 보존 — 먼저 한다

Supabase 는 "검증 완료 전까지 폐기하지 않는다"고 되어 있지만 **그 약속에 기대지 않는다.**
48장 85.2MB 를 우리 버킷의 **격리 프리픽스**에 원본 그대로 올린다.

```
icaros-web/legacy-posts/<원본파일명>
```

- 원본을 **가공하지 않는다.** 정책(1600px·WebP·2MB)은 화면에 나가는 사본에 적용하는 규칙이지
  보존본에 적용할 규칙이 아니다.
- `media` 테이블에 넣지 않는다. 이건 화면에 나가는 미디어가 아니라 **아카이브**다.
  `media` 에 넣으면 `/api/media` 로 서빙 가능해지고, 그 순간 "안 쓰는데 서빙되는 것"이 생긴다.
- 버킷은 오늘 Versioning 을 켰으므로 실수로 지워도 되돌릴 수 있다.
- md5 매니페스트를 함께 올려 나중에 무결성을 대조할 수 있게 한다.

> ⚠️ **이 단계는 되돌리기 어려운 축에 든다** — S3 쓰기다. 실행 전 승인.

### 3.2 URL 치환 규칙을 코드로 고정

본문은 마크다운이고 참조는 전부 `![alt](<supabase-url>)` 형태다.
치환을 사람이 하지 않는다 — **URL → 새 URL 매핑 표를 만들고 그 표로만 바꾼다.**

```
legacyUrl → { file, md5, bytes, newUrl }
```

- 매핑에 없는 URL 이 본문에 하나라도 남으면 **실패로 처리**한다. 조용히 지나가면
  게시판에 깨진 이미지가 남고, 그건 원본이 사라진 뒤에야 발견된다.
- 치환 후 본문을 다시 스캔해 `supabase.co` 가 **0건**인지 확인한다.
- 원본 본문과 치환본을 나란히 저장해 사람이 대조할 수 있게 한다.

### 3.3 `review` 1건 판정

`ICX-1A Launch` 가 ESSENTIA 에 이미 있는지 본문으로 대조한다.
읽기는 지금도 되므로(`listIcarosPosts`) 우리가 할 수 있다.
**중복이면 `skipped` 로 옮긴다** — 같은 발사가 두 번 올라가는 것이 빠지는 것보다 나쁘다.

### 3.4 최종 페이로드 산출

`migrate:posts` 가 이미 만드는 페이로드에 §3.2 의 치환본을 반영해 확정판을 만든다.
여기까지가 **우리가 D1 없이 끝낼 수 있는 마지막 지점**이다.

## 4. D1 이 붙은 뒤 (상대 협조 필요)

1. **이미지 업로드** — 안 A 면 ESSENTIA 업로드 API 로 48장을 올리고 반환된 이름으로
   §3.2 매핑의 `newUrl` 을 채운다. 안 B 면 우리 버킷 사본을 `media` 에 등록하고
   `/api/media/{id}` 로 채운다.
2. **본문 재치환** — 매핑이 채워졌으니 §3.2 를 다시 돌린다. 스캔 0건 확인.
3. **글 생성** — 서비스 계정 FK(D13)로 19건(또는 18건) 생성.
   `createdAt` 은 **원문 값을 보존**한다. 이관 시각으로 덮으면 13개월치 기록이 하루로 접힌다.
4. **검증** — `/posts` 를 우리 사이트에서 열어 19건이 보이고 이미지가 전부 뜨는지 확인.
   이건 우리가 한다.

## 5. 위험과 방어

| 위험 | 왜 실제 위험인가 | 방어 |
|---|---|---|
| **Supabase 가 먼저 죽는다** | 원본 85MB 가 그 안에만 있다 | §3.1 을 **가장 먼저** 한다. 로컬 사본은 세션이 끝나면 사라진다 |
| **본문에 치환 안 된 URL 이 남는다** | 원본이 사라진 뒤에야 깨진 게 보인다 | 치환 후 `supabase.co` 스캔 0건을 **실패 조건**으로 |
| **중복 게시** | 같은 발사가 두 번 올라간다 | `skipped` 1건 + `review` 1건 판정을 업로드 **전에** 끝낸다 |
| **날짜 소실** | 13개월 기록이 이관일 하루로 접힌다 | `createdAt` 원문 보존을 인수 조건에 명시 |
| **`forum/` 에 잘못 쓴다** | 프리픽스 교차 삭제 사고 전력 (07 §0-4) | 코드 경계(`isOwnedKey`)와 IAM 정책 **둘 다** 그대로 둔다. 안 A 는 우리가 직접 쓰지 않고 상대 API 를 부른다 |
| **21개가 정책 상한 초과** | 그대로 화면에 나가면 목록 전송량이 무너진다 | 보존본은 원본 그대로, **화면용 사본만** 정책 적용. 두 벌을 구분한다 |

## 6. 순서

```
[지금]  3.1 원본 보존 (S3 쓰기 — 승인 필요)
         ↓
        3.3 review 1건 판정   ← 읽기만, 병렬 가능
         ↓
        3.2 치환 규칙 + 매핑 표
         ↓
        3.4 최종 페이로드 확정          ← 여기까지 우리 손으로 끝
========================================
[D1 후] 4.1 이미지 업로드 (A 또는 B)
         ↓
        4.2 본문 재치환 · 스캔 0건
         ↓
        4.3 글 19건 생성 (서비스 계정 FK · createdAt 보존)
         ↓
        4.4 /posts 검증                 ← 우리가 확인
```

## 7. 미결 — 사람이 정해야 하는 것

1. **§2 의 A / B 중 무엇으로 가는가.** D1 착수 시점에 달려 있다.
2. **ESSENTIA 에 업로드 API 가 있는가.** 어댑터는 읽기만 구현돼 있어 확인이 필요하다.
   없으면 A 는 성립하지 않고 B 가 유일한 선택이 된다.
3. **`review` 1건을 누가 판정하는가.** 본문 대조는 우리가 할 수 있지만
   "같은 사건을 두 번 적었는가"는 팀이 판단할 문제다.
4. **원본 보존본을 언제까지 두는가.** 무기한이면 비용이, 기한이 있으면 그 뒤 복구 불가가 대가다.
