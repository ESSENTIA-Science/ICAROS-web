## P2 — 장애의 재발 경로가 코드로 봉인돼 있지 않다

`src/lib/db/connection.ts:170-184` 의 값들이 장애에서 배운 결과다:
```ts
max: 3,
idleTimeoutMillis: 10_000,     // 60초로 올렸다가 프로덕션을 죽인 값
connectionTimeoutMillis: 10_000,
```

**그런데 이것을 지키는 것은 주석뿐이다.**
누군가(또는 미래의 본인이) 다시 60으로 올리면 같은 장애가 재현되고,
그때는 주석을 읽지 않았을 가능성이 높다.

`buildPoolConfig()` 는 **환경변수만 받아 객체를 반환하는 순수 함수다.**
테스트 5줄이면 봉인된다:

```ts
it('serverless pool stays small — 2026-08-27 incident', () => {
  const cfg = buildPoolConfig()
  expect(cfg.max).toBe(3)
  expect(cfg.idleTimeoutMillis).toBe(10_000)
})
```

**이것이 이 저장소에서 비용 대비 효과가 가장 큰 한 걸음이다.**
사후분석을 주석이 아니라 테스트로 남긴다.

## 남은 관측 (대장 A1)

배포 직후 cold fan-out으로 커넥션이 최대 36까지 튄다.
이미지 최적화기 캐시가 배포마다 비고 새 인스턴스의 메모리 캐시도 비어,
변형 25개 × 여러 인스턴스가 동시에 첫 조회를 한다.

대장의 결론은 **"관측만 한다"** 이고 근거(경고선 60, 위험선 85, 현재 36)가 타당하다.
`max: 1` 은 Fluid Compute 구조상 커넥션 문제를 지연 문제로 바꾼다.

**이 감사도 같은 결론이다.** 지금 손대지 않는다.
