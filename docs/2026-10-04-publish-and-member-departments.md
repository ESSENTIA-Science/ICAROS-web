# 게시 실패 조사와 멤버 다중 부서 패치 — 2026-10-04

## 운영 관측

- 최근 CodeBuild 7건은 모두 성공했다. 2026-10-03 23시대의 빌드 4건은 각각 약 5~7분이 걸렸다.
- 게시 버전 7·8은 새 요청이 도착해 `superseded`로 종료됐고, 뒤의 9·10은 게시 완료됐다. 현재 게시 상태는 버전 10이며 활성 작업은 없다.
- 완료 callback이 약 46초 동안 게시 상태 행의 잠금을 잡았다. 같은 시간 CMS의 4초 간격 상태 조회 두 건이 API Lambda의 30초 제한에 걸렸다.
- 따라서 화면의 일반적인 “게시 실패” 문구에는 새 작업으로 대체된 경우가 포함됐고, 완료 단계에서는 조회 타임아웃도 발생했다. 이 기록만으로 개별 사용자의 화면을 특정할 수는 없다.

## 준비한 변경

- 게시 상태 조회는 완료 callback의 쓰기 잠금을 기다리지 않고 커밋된 작업 행을 읽는다. `superseded`는 실제 빌드 실패와 구분해 안내한다.
- CMS의 예상 반영 시간을 운영 관측값에 맞춰 5~8분으로 고쳤다.
- 멤버의 `departmentIds`를 순서 있는 복수 선택으로 저장한다. 새 관계 테이블은 기존 단일 소속을 이관하고, 부서 삭제·재배정도 여러 소속을 처리한다.
- 공개 스냅샷에 `squads`를 추가한다. 공개 멤버 페이지는 선택된 각 부서에 해당 멤버를 표시하며 기존 스냅샷의 단일 `squad`도 읽는다.

## 검증과 적용 순서

API 테스트 215개, Web/CMS 테스트, 양쪽 typecheck·lint, API build가 통과했다.
PostgreSQL 17 임시 DB에서 이관, 복수 소속 생성·수정, 이미 소속된 부서로 재배정,
소속 해제를 확인했다. 운영 DB의 새 마이그레이션은 아직 적용하지 않았다.

게시 상태 조회 핫픽스 `b245250`은 2026-10-04 API·callback Lambda에 적용했다.
CloudFormation 갱신이 완료됐고 두 함수의 코드 해시가 배포 파일과 일치한다.
CMS와 공개 사이트 HTTP 200, 인증 API의 예상 응답, 완료 이벤트 연결을 확인했다.
실제 관리자 계정으로 새 게시를 실행한 검증은 아직 하지 않았다.

다중 부서 기능은 운영 스키마 백업과 승인 후 API 마이그레이션 009를 적용하고,
API·CMS를 갱신한 다음
새 전체 게시로 공개 스냅샷을 생성해야 한다. 현재 보관된 이관 계정 URL은 운영 API의
DB 주소와 다르고 인증도 실패했다. 올바른 이관 접속 경로를 확인하기 전에는 적용하지 않는다.

운영 로그 원문과 접속 정보는 추적하지 않는 `docs/.local/`에만 둔다.
